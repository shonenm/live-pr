# 戦略: ローカルを PR の主戦場にする (2026-11)

## この文書の位置づけ

2026-11-10 に合意した方向転換と、その後の設計判断をまとめる。個々の PR や
ドキュメントはこの文書に従う。方向が変わったらこの文書を先に直す。

旧方針（意思決定タイムラインを製品の中心に置く）の計画は
[legacy/roadmap.md](legacy/roadmap.md) に残してある。タイムライン自体は柱の
1 つとして残る。

## なぜ方向を変えるか

旧方針の命題は「GitHub の PR は最終結論しか残さない。ローカルで最初から PR
を意識し、意思決定の変更過程を残す」だった。

開発速度が上がり、これだけを中心に据える価値は薄れた。変更 1 件あたりの
寿命が短くなり、過程を読み返す機会が減った。一方で、次の負担は速度が上がる
ほど重くなっている。

- GitHub Actions の従量課金。agent が大量に push すると、そのたびに CI が走る。
- self-hosted runner を使う場合の、サーバーの CPU とメモリの逼迫。
- GitHub の UI と通信の往復による待ち時間。

## 命題

ローカルを PR の主戦場にする。PR に関わる作業（書く、見る、確かめる、agent
とやり取りする、マージする）をローカルの 1 つの TUI で完結させ、GitHub には
結果を渡す。

GitHub の PR をターミナルに映すだけでは足りない。ローカルにあるからこそ
できることを、次の 6 つの柱として積む。

## 柱

### 1. ローカルでしかできない表現と見せ方

GitHub の画面の制約に縛られない見せ方をする。

- PR 一覧を、関連するタスクごと、または実装した worker ごとにまとめる。
- PR の説明を、GitHub の PR で可能な Markdown と画像・動画以上の表現にする。

現状: 一覧には view、filter、stack によるまとめがある。説明は Markdown と
図の描画までである。タスク単位と worker 単位のまとめ、および説明の拡張は
未着手で、何を表現の単位にするかは未決定である。

### 2. CI の実行と保証

リポジトリのチェックをローカルで実行し、その結果をリモートが信頼できる形で
保証する。詳細は後述の「CI の実行と保証の設計」にまとめる。

現状: 実行、署名、検証、TUI の表示まで実装済みで、マージ前である（#368、
#369）。

### 3. agent との対話

GitHub の PR 上で agent にコメントするのと同じ感覚で、ローカルの PR から
agent とやり取りする。

- live-pr から @mention つきのコメントで指示を出すと、作業中のセッションを
  汚さずに裏で実行され、回答がコメントとして返る。
- 行に対するコメントと、それを使ったやり取り。レビュー用のツールとの境界は
  これまでどおり切る。初期の想定は native、hunk、nvim の 3 つで、hunk を
  内部で使うこともできる。

現状: 行コメントは GitHub のレビューとして下書きと提出ができる。review pane
は差し替え可能である。@mention による裏での実行は未着手である。

### 4. local と remote の両方の管理

ローカルにしかない作業と、GitHub にある PR を同じ画面で扱う。

現状: LOCAL / LIVE / REMOTE のモード、未 push の commit と作業ツリーの表示、
他の PR を checkout せずに見る機能がある。

### 5. ローカルであることを活かした高速化

通信と GitHub の UI を待たない。キャッシュを使うが、容量は可能な限り小さく
保つ。

現状: GitHub のデータはキャッシュを先に表示し、裏で更新する。増分取得は
残作業である。

目標値（暫定。計測の仕組みを用意した時点で見直す）:

| 指標 | 目標 |
| --- | --- |
| 起動から、キャッシュにある一覧または詳細が表示されるまで | 100 ms 以内 |
| ディスク上の状態とキャッシュの合計（1 リポジトリあたり） | 10 MB 以内 |

最適化は、計測してこの目標を超えた箇所にだけ行う。言語やファイル形式の
刷新は、原因がそこにあると計測で示された場合に限って検討する。

### 6. 起票前から存在する PR

PR を GitHub に起票する前から、ローカルには PR が存在する。それを意識して
開発を進め、意思決定の過程を残す。

現状: `decision` / `pivot` / `note` の記録、agent の Stop hook による要約、
タイムラインを本文に載せる `live-pr pr publish` がある。旧方針では製品の中心
だったが、新方針では柱の 1 つである。

## CI の実行と保証の設計

### 原則

- **ローカルの環境を流用する。** clone やコンテナによる完全な隔離は最後の
  手段とする。手元のツールチェーンとキャッシュを使えることが、この製品の利点
  である。
- **リモートを正とする。** 証跡がない、または一致しない場合、リモートの job
  は通常どおり実行される。ローカル CI はリモートを廃止するものではなく、
  省略できる場合に省略するものである。
- **CI の解釈部を持たない。** チェックは「名前 = コマンド」とし、workflow の
  YAML は読まない。ローカルとリモートが同じスクリプトを呼ぶことで両者を
  揃える。GitHub Actions の再現は act などの既存ツールの領分であり、必要な
  利用者はそれをコマンドとして指定する。
- **「agent が単独では開けられない」を保証の水準とする。** 「改ざん不可能」
  とは言わない。署名鍵が agent の手の届かない場所にあることが前提になる。
- **導入側の手間は許容し、skill で軽くする。** 検証 job の追加と job の
  `if:` は導入側が書く。手順は live-pr の skill が案内する。
- **独自言語と証明系は採らない。** live-pr 専用のパッチ言語や、Lean などに
  よる等価性の証明は検討したうえで見送った。得られる保証に対して、導入と
  保守の負担が大きい。

### 仕組み

| 段階 | 内容 |
| --- | --- |
| 実行 | TUI の `R` または `live-pr ci run` が `[ci.local.checks]` のコマンドを checkout で実行する |
| 条件 | 実行の前後で checkout が clean であり、tree が変わっていないこと |
| 署名 | 成功したチェック名と tree のハッシュを SSH 鍵で署名する。鍵はグローバル設定からのみ読む |
| 保存 | HEAD の tree オブジェクトへの git note（`refs/notes/live-pr`）として push する |
| 検証 | リモートの検証 job が、base リビジョンの `.live-pr/allowed_signers` で署名を確かめる |
| 省略 | 検証 job の出力が `attested` のチェックに対応する job を `if:` でスキップする |

証跡は commit ではなく tree を指す。同じ tree になる squash や rebase では
有効なままで、base が動いた場合やファイルが 1 つでも違う場合は無効になる。

信頼の境界は次のとおり。

- 偽造した結果と、別の tree へコピーした note は検証で拒否される。
- PR 自身が追加した署名者は信頼されない。鍵は base から読む。
- gitignore 対象のファイルとローカルのツールチェーンは信頼する。その保険
  として、既定ブランチへの push ではリモートで全 job を実行する。
- チェック自体を弱める変更と、リモートの job がローカルのコマンドより多くを
  実行している場合の差分は、署名では防げない。レビューで見る。

### 先行ツールとの違い

2026-11 の調査時点での整理である。

| ツール | やっていること | live-pr との違い |
| --- | --- | --- |
| gh-signoff（Rails の `bin/ci`） | ローカルで通したことを commit status として自己申告する | 署名がなく、信頼ベース |
| tetriz-ai/local-ci | チェック結果を git note に記録し、マージゲートの action で確認する | 思想は最も近い。note は署名されていない |
| redwoodjs/local-ci | 公式 runner をローカルで動かし、構造化イベントを出す | Docker が前提。リモートが引き続き門番 |
| nektos/act、wrkflw | workflow をローカルで再現する | 実行のみ。証跡もレビューもない |
| Witness、cilock | in-toto による署名つきの証跡 | 汎用の証跡基盤。PR の作業画面を持たない |

個々の要素はどれも既存である。空いているのは、tree に束縛した署名つきの
証跡でリモートの job を省略することと、それを他の柱と同じ TUI に載せることの
組み合わせである。要素単体の優位は浅く、統合に価値がある。

### 残りの作業

1. 署名者を登録し、証跡つきで job が実際にスキップされることを確かめる。
   ssh-agent や Secure Enclave の鍵での署名も確かめる。
2. マージゲート。TUI の `m` で、証跡のない変更のマージを止める。
3. step 単位の進捗とログ。GitHub Actions と同じ粒度で見られるようにする。
   出力のストリーム化、ログの保存、ログを読むペイン、`::group::` の解釈で
   実現する。
4. strict モード。検証に失敗したときにフォールバックせず、job を失敗させる
   選択肢。
5. GitHub Actions 以外の CI。検証スクリプトは sh で書かれているので、必要
   なのは CI ごとの検証 job の雛形だけである。最初の候補は Woodpecker。
