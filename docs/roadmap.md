# ロードマップ (2026-11)

## この文書の位置づけ

[アーキテクチャ](architecture.md) は、何を作るか、なぜそうするか、すでにある
仕組みを書く。この文書は、まだないものと、それをどの順でどのリリースに
入れるかを書く。柱や設計の説明はここでは繰り返さず、柱の番号で参照する。
両者が食い違ったらアーキテクチャを正とし、この文書を直す。

日付は置かない。各段階は「次へ進む条件」で区切る。

| 系統 | ブランチ | 中身 | 状態 |

## alpha で進める順番

柱の番号はアーキテクチャのものである。順番は 2026-11-12 に合意した。

### A1. 柱 2 を実運用に載せる

実際にリモートの job が省略されることは、まだ確かめていない。仕様は
2026-11-13 に [判断の指針](principles.md) に沿って決めた。

1. 検証 job が失敗すると、それに依存する job が実行されずに成功扱いになる
   穴を塞ぐ。省略は、検証 job が成功し、かつ `attested` を出したときに
   限る。空白のチェックは検証 job から分ける。省略しなかった理由（base に
   追従していない、など）を検証スクリプトが出す。
2. このリポジトリに署名者を登録し、証跡つきで `test` job がスキップされる
   ことを確かめる。
3. 手元で証跡を検証する処理。`m` の確認画面にチェックごとの状態（証跡あり、
   リモートで実行中、通過、失敗）を出し、すでに有効な証跡がある tree では
   実行を省く。
4. 複数の worktree から同時に実行したとき、証跡の書き込みが失われない
   ようにする。書き込みをリポジトリ単位で直列化し、push が拒否されたら
   やり直す。
5. job を required check にする手順を docs に書く。

決めたことは次のとおり。

- 省略の条件に base への追従を含めない。リモートが試験する tree（PR の
  マージ結果）と一致したときだけ省略する。追従を必須にするかはルールセット
  が決める。
- live-pr はマージを止めない。required check にしておけば、GitHub が「証跡
  があるか、リモートで通ったか」で止める。
- 同時実行の数を live-pr は制限しない。絞りたい利用者はチェックのコマンドを
  `flock` などで包む。
- 証跡の形式は今のままにし、in-toto には寄せない。
- 署名者の手元での改ざんは防がない（2026-11-14）。署名者と同じ OS ユーザー
  で動くもの（agent を含む）は toolchain やキャッシュを書き換え、鍵も使える
  ので、証跡からは見分けられない。防ぐには隔離か管理者権限が要り、利用者を
  限定する。ビルドキャッシュ（Bazel、Nx、Gradle）も開発者の機械の結果を
  信頼せず、同じ型の道具（gh-signoff、tetriz-ai/local-ci）も自己申告と明言
  している。省略を使うことは署名者の機械を信頼することとして文書にし、
  受け入れない利用者は署名者を登録しなければリモートですべて実行される。

進む条件: このリポジトリの PR が、日常的にローカルの証跡でリモートの job を
省略している。

### A2. 計測の仕組み（柱 5）

柱 5 の目標値は暫定で、測る手段がない。機能を足す前に測れるようにし、以降の
柱が目標を割っていないかを確かめられるようにする。

1. 起動から最初の表示までの時間と、ディスク上の容量を出すコマンドまたは
   ベンチマーク。
2. 計測して目標を超えた箇所だけを直す。増分取得はここで要否を判断する。

進む条件: 2 つの指標が再現可能な手順で測れ、目標値を見直し済みである。

### A3. CI の進捗とログ（柱 2 の続き）

1. step 単位の進捗とログ。出力のストリーム化、ログの保存、ログを読むペイン、
   `::group::` の解釈。
2. strict モード。検証に失敗したとき、フォールバックせず job を失敗させる。
3. GitHub Actions 以外の検証 job の雛形。最初の候補は Woodpecker。
4. act の host モードを、スクリプトを持たないリポジトリのコマンドとして
   使えるかを確かめる。

進む条件: 失敗したチェックの原因を、TUI から離れずに特定できる。

### A4. agent との対話（柱 3）

1. 設計をアーキテクチャに書き足す。@mention の宛先、裏で実行する手段、回答の返し方、
   作業中のセッションとの分離。
2. @mention つきのコメントで指示を出し、回答がコメントとして返る。
3. 行コメントを使ったやり取り。

進む条件: PR 上の指摘から修正までを、agent のセッションに切り替えずに
回せる。

### A5. ローカルならではの見せ方（柱 1）

1. 設計をアーキテクチャに書き足す。まとめる単位（タスク、worker）を何から得るか。
2. PR 一覧のタスク単位と worker 単位のまとめ。
3. PR の説明の拡張。

A5 は表現の単位が未決定で、A4 の結果（agent と PR の対応づけ）に依存する
見込みが高い。そのため最後に置く。2.0.0 に入れず 2.1 に回す候補である。

## 2.0 で壊す変更

## 2.0.0 の条件

- A1 から A4 が「進む条件」を満たしている。A5 を含めるかは A4 の後に決める。
- 壊す変更がすべて入り、1.x からの移行手順がリリースノートにある。
- README と prior-art が新しい方針で書き直されている。
- 2 つの性能指標が目標値の内側にある。
- beta を自分の日常の開発で使い、1.x に戻る理由が残っていない。

## 1.x と共通の既知の課題

main で直し、1.x にも該当するものは `release/1.x` に取り込む。

- 開いていない view のタブ件数が、古いキャッシュのまま表示される。
- 全角文字を含む行が毎フレーム再描画される（upstream の ultraviolet の挙動）。
- 端末の高さが足りないと、ヘルプのポップアップが切れる。
