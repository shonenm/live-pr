# 判断の指針

## この文書の位置づけ

設計や仕様で迷ったときに立ち返る方針を書く。何を作るかは
[architecture.md](architecture.md)、順番は [roadmap.md](roadmap.md) に書き、
ここには書かない。個別の判断がこの指針と食い違う場合は、どちらを直すかを
決めてから進める。

## 1. 拡張できる形にし、利用者を限定しない

特定の環境や使い方を前提にした作りにしない。今は対応していなくても、
あとから足せる形にしておく。

- **ホスティング**: 今は GitHub だけに対応するが、GitLab などを足せない
  作りにはしない。
- **使い方**: TUI だけでなく、CLI や agent から同じことができるようにする。
- **厳密さ**: セキュリティや検証の強さは、利用者が設定で選べるようにする。
  既定値は GitHub の挙動に合わせ、それより厳しくする設定は利用者が選んだ
  ときだけ効かせる。
- **拡張**: 利用者が自分の道具を差し込めるようにする。review pane の差し
  替えがその例である。

## 2. 再発明しない

アイデアは外部のプロダクトや OSS から借りる。新しい仕組みを考える前に、
同じ問題を解いている先行例を調べる。

- 既存のツールでできることは、そのツールを使う（act、`ssh-keygen -Y`、
  git notes など）。
- 自前で作る場合も、確立した方式やベストプラクティスに従う（ファイルロック、
  証跡の形式など）。
- 調べた先行例と、そこから何を採り何を採らなかったかを、設計の文書に残す。

## 3. GitHub の PR でできることを削らない

情報を足すことはしても、GitHub の PR でできること、見られる情報を勝手に
削らない。

- GitHub が出している状態（チェック、レビュー、マージの可否など）は、
  live-pr でも見えるようにする。要約するときも、元の情報にたどり着ける
  ようにする。
- GitHub の判定を live-pr が上書きしない。GitHub が通すものを live-pr が
  止めない。止めたい利用者のためには 1 の設定として用意する。

## 適用した例

2.0 の A1（ローカル CI を実運用に載せる）の仕様を決めたとき（2026-11-13）に
この指針を使った。

| 論点 | 判断 | 根拠 |
| --- | --- | --- |
| リモートの job を省略する条件に、base への追従を含めるか | 含めない。リモートが試験する tree と一致したときだけ省略する | 3。追従の要否はルールセットが決める |
| TUI の `m` で、証跡のない変更のマージを止めるか | 既定では止めない。確認画面にチェックごとの状態を出す | 3。required check にすれば GitHub が同じ条件で止める。止める設定は 1 として後から足せる |
| 複数の worktree からの同時実行を live-pr が制限するか | 制限しない。証跡の書き込みだけを直列化する | 1、2。資源の配分は利用者の領分で、`flock` などの既存の道具で包める |
| 証跡をどの方式で検証するか | `ssh-keygen -Y` の署名と git notes を使う。in-toto の形式は今は採らない | 2。既存の道具に乗り、形式は必要になったときに寄せる |
| 署名者の手元での改ざん（agent を含む）を live-pr が防ぐか | 防がない。省略を使うことは署名者の機械を信頼することだと文書に書き、リモートに任せる利用者は従来どおり使える | 1、2。防ぐには隔離か管理者権限が要り利用者を限定する。ビルドキャッシュも開発者の機械の結果を信頼しない |
